## 2. Architecture

The principle is that **the 177 skills are instruction sets, not 177 features**. Coverage comes from shared components, adapters, profile images and viewers, and the registry maps each skill onto them.

### 2.1 Capability registry (`core.registry`)

The registry is server-side and read-only at runtime. It is built from the reviewed registry file and pinned by catalog commit plus registry digest, and that pin is included in the run's `skills_digest`. Each entry holds:
- id, catalog path and SHA-256
- capability card (≤300 tokens)
- adapter ids and profile image
- connection requirements and license status
- prerequisite ids with gated stage and unlock condition
- **per-status evidence fields**

A capability can be enabled only if:
- it is implemented and validated, with evidence;
- none of its prerequisites gates `enable`;
- required scientific signoff has been recorded.

`GET /capabilities` gains safe readiness counts and reasons, with no skill names exposed in product UI.

### 2.2 Task-relevant instruction loader (`core.instruction_loader`)

1. **Select (server):** rank the registry cards, not full SKILL.md files, against the request and the selected input types. Shortlist at most K enabled capabilities (default K = 3).
2. **Approve (owner):** the plan shows steps, versions, prerequisites, destinations and cost in scientific terms. Capability ids and instruction hashes become part of the plan digest.
3. **Load (worker):** the worker loads only the approved bundle and verifies hashes. SKILL.md sections and resources load on demand, under an instruction-token budget charged to the run. Instructions never widen tools, destinations, packages or secrets.
4. Hermes native skill discovery stays disabled unless a separate compatibility and containment proof is accepted.

### 2.3 Typed tool host (`core.typed_tool_host`) and shared adapters

- Tools are reviewed and schema-validated. Each call becomes a journaled broker operation or a contained executor step, with budget reservation, owner-wait on unknown outcome, no-resend and checkpoints, the same as B3/B5.
- `OperationRequest.kind` stays a closed set. New kinds (`execute`, `fetch_dataset`, `remote_job`) are added only by a parent-owned contract change with tests.

### 2.6 Protocols

MCP/A2A expose only **enabled** capabilities through the same domain services and authority as REST. `ad.mcp_client` reuses the I1 outbound policy, release approval and reconciliation. There is no second orchestrator.

### 2.7 Policies preserved

- Plan approval binds capability ids and instruction hashes.
- The broker is the only egress.
- Budgets and checkpoints cover instruction tokens, compute and paid calls.
- An unknown external outcome waits for the owner and is never resent.
- Secrets stay server-side as grants.
- Releasing data externally needs explicit approval.
- Packages come only from scanned images. No `pip install` from instructions.

The builder sets `value: true` only when evidence exists and no prerequisite gates that stage, and it rejects a status-ladder violation.

| Status | Evidence | Requires |
|---|---|---|
